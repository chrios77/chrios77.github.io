```
1. 자바에서는 순수 추상 클래스를 더 편리하게 사용할 수 있는 무엇인가를 제공하는데 이것이 무엇인가? ⇒ 자바에서는 순수 추상 클래스를 더 편리하게 사용할 수 있는 인터페이스라는 기능을 제공한다.
2. 인터페이스는 어떤 키워드를 사용하는가? ⇒ 인터페이스는 class가 아니라 interface 키워드를 사용하면 된다.
3. 인터페이스는 뭐와 같고 이것의 특징에 어떤 특징들이 들어가 있는가? ⇒ 인터페이스는 순수 추상 클래스와 같고, 순수 추상 클래스는 인스턴스를 생성할 수 없다, 상속 시 모든 메소드를 오버라이딩 해야 한다, 주로 다형성을 위해 사용된다, 라는 특징이 있고 인터페이스는 이 특징들에 인터페이스의 메소드는 모두 public, abstract가 들어가고, 메소드에 public abstract를 생략할 수 있다. 참고로 이는 생략하는 것을 권장한다. 마지막으로 인터페이스는 다중 구현 혹은 다중 상속을 지원한다.
4. 인터페이스에 멤버 변수를 넣을 수 있는가? O/X ⇒ O, 인터페이스에서 멤버 변수는 public, static, final이 모두 포함되었다고 간주된다. final은 변수의 값을 한 번 설정하면 수정할 수 없다는 뜻이다. 
5. 자바에서 static final을 붙이면 어찌되는가? ⇒ 자바에서 static final을 사용해 정적이면서 고칠 수 없는 변수를 상수라 하고, 관례상 상수는 대문자에 언더스코어(_)로 구분한다.
6. 클래스 상속 관계와 인터페이스 구현 및 상속은 UML에서 어떻게 표시하는가? ⇒ 클래스 상속 관계는 UML에서 실선을 사용하지만 인터페이스 구현 및 상속은 UML에서 점선을 사용한다.
7. 왜 인터페이스를 구현이라고 하는가? ⇒ 부모 클래스에 있는 기능을 자식 클래스에서 만들어내야 하기에 구현이라고도 한다.
8. 인터페이스는 왜 만들어지는가? ⇒ 인터페이스는 보통 여러 곳에서 사용하기 위해 만들어진다.
9. 인터페이스를 상속 받을 때는 뭘 사용하는가? ⇒ implements
10. 상속 vs 구현?? ⇒ 부모 클래스의 기능을 자식 클래스가 상속 받는다고 할 때, 클래스는 상속받는다고 표현하지만, 부모 인터페이스의 기능을 자식이 상속받을 때는 인터페이스를 구현한다고 표현한다. 이렇게 표현하는 이유는 상속은 이름 그대로 부모의 기능을 물려받는 것이 목적이지만 인터페이스는 모든 메소드가 추상 메소드이다. 따라서 물려받을 수 있는 기능이 없고, 오히여 인터페이스에 정의한 모든 메소드를 자식이 오버라이딩해서 기능을 구현해야하기에 구현한다고 표현한다. 또한, 인터페이스는 메소드 이름만 있는 설계도이고, 이 설계도가 실제 어떻게 작동하는지는 하위 클래스에서 모두 구현해야 하기에 인터페이스의 경우 상속이 아니라 해당 인터페이스를 구현한다고 표현한다.
11. 자바 입장에서 상속과 구현은 어떻다고 볼 수 있는가? ⇒ 자바 입장에서 상속과 구현은 사람이 푷련하는 단어만 다를 뿐이지 똑같다. 일반 상속 구조와 동일하게 작동한다.
12. 인터페이스를 사용하는 이유는 무엇인가? ⇒ 모든 메소드가 추상 메소드인 경우 순수 추상 클래스를 만들어도 되고, 인터페이스를 만들어도 된다. 근데 왜 인터페이스를 사용해야 할까? 그 이유는 제약적 이유와 다중 구현적 이유가 있다.
13. 인터페이스를 사용하는 이유 중 하나인 제약은 무엇인가? ⇒ 인터페이스를 만드는 이유는 인터페이스를 구현하는 곳에서 인터페이스를 반드시 구현하라는 규약을 주는 것이다. 인터페이스의 규약은 반드시 구현해야 한다는 것인데 순수 추상 클래스의 경우 미래에 누군가를 그 곳에 실행 가능한 메소드에 끼워 넣을 수 있어야 한다. 이렇게 되면 추가된 기능을 자식 클래스에서 구현하지 않을 수도 있고, 또 더는 순수 추상 클래스가 아니게 된다. 인터페이스는 모든 메소드가 추상 메소드이기에 이런 문제를 원천 차단할 수 있다.
14. 인터페이스를 사용하는 이유 중 하나인 다중 구현은 무엇인가? ⇒ 자바에서 클래스 상속은 부모를 하나만 지정할 수 있는 반면, 인터페이스는 부모를 여러 명 두는 다중 구현, 즉, 다중 상속이 가능하다.
15. 좋은 프로그램이란 무엇인가? ⇒ 좋은 프로그램은 제약이 있는 프로그램이다.
16. 자바 8에서 등장한 default 메소드나 자바 9에서 등장한 private 메소드를 사용하면 인터페이스를 사용할 수 있지 않은가? ⇒ 자바 8에서 등장한 default 메소드를 사용하면 인터페이스도 메소드를 구현할수 있으나 이것은 예외적으로 아주 특별한 경우에만 사용해야 한다. 이는 자바 9에서 등장한 인터페이스의 private 메소드도 만찬가지이다.
17. 자바는 다중 상속을 지원하는가? ⇒ 자바는 다중 상속을 지원하지 않는다. 그래서 extends 대상은 하나만 선택할 수 있다. 이는 부모 클래스를 하나만 선택할 수 있다는 뜻이다. 물론 부모 클래스가 다른 부모 클래스를 가지는 것은 괜찮다.
18. 자바가 클래스의 다중 상속을 지원하지 않는 이유는 무엇인가? ⇒ 다중 상속을 사용하게 되면 자식 클래스 입장에서 어떤 메소드를 호출할 때 어떤 부모의 메소드를 사용해야 할지 애매한 문제가 발생한다. 이를 다이아몬드 문제라고 한다. 그리고 다중 상속을 사용하면 클래스 계층 구조가 매우 복잡해질 수 있기에 자바는 클래스의 다중 상속을 허용하지 않는다. 대신 인터페이스의 다중 구현을 허용하여 이러한 문제를 피한다.
19. 자바에서 인터페이스의 다중 구현을 허용하는 이유는 무엇인가? ⇒ 인터페이스는 모두 추상 메소드로 이뤄져 있기 때문이다. 예를 들어, 부모 클래스 2개와 자식 클래스 하나가 있다고 칠 때, 부모 클래스에 같은 메소드가 있다면 자식 클래스 입장에서 어떤 부모 클래스의 메소드를 사용할지 결정해야 해 다이아몬드 문제가 발생한다. 그러나 인터페이스 자신은 구현을 가지지 않는다. 대신 인터페이스를 구현하는 곳에서 해당 기능을 모두 구현해야 한다. 부모 클래스가 같은 이름의 메소드를 제공하지만 이 기능은 자식 클래스가 구현한다. 그리고 오버라이딩에 의해 자식 클래스에 있는 메소드가 호출되기에 결과적으로 두 부모 클래스 중에 어떤 한 부모의 메소드를 선택하는 것이 아니라 자식 클래스에 있는 메소드를 사용하면 된다. 이러한 이유로 인터페이스는 다이아몬드 문제가 발생하지 않으며 인터페이스의 경우 다중 구현을 허용한다.
20. 자바에서 다중 구현은 어떻게 할 수 있는가? ⇒ public class ImplementsC implements InterfaceA, InterfaceB 처럼 implements 다음에 ,로 여러 인터페이스를 구분하면 된다. 
21. 자바에서 클래스 상속과 인터페이스 구현을 함께 사용하는 것이 가능한가? O/X ⇒ O 예를 들어, public class Bird extends AbstractAnimal implements FLy, Eat(){} 처럼 사용할 수 있다. 이때 상속은 하나만 쓸 수 있고, 인터페이스는 여러 개 사용할 수 있다.
22. 객체 지향의 특징은 무엇인가? ⇒ 추상화, 캡슐화, 상속, 다형성
23. 객체지향 프로그래밍이란? ⇒ OOP은 컴퓨터 프로그램을 명령어의 목록으로 보는 시작에서 벗어나 여러 개의 독립된 단위인 객체들의 모임을 파악하고자 하는 것이다. 각각의 객체는 메시지를 주고 받고, 데이터를 처리하여 협력한다. 또한, OOP은 프로그램을 유연하고 변경이 용이하게 만들기에 대규모 소프트웨어 개발에 많이 사용된다.
24. OOP에서 유연하고 변경이 용이하다는 것은 무엇인가? ⇒ 레고 블럭을 조립하듯이, 키보드, 마우스를 갈아 끼우듯이, 컴퓨터 부품을 갈아 끼우듯이, 컴포넌트를 쉽고 유연하게 변경하면서 개발할 수 있는 방법을 말한다.
25. 다형성을 실세계에 비유해보면? ⇒ 다형성을 실세계에 비유해보면 실세계와 객체 지향을 일대일로 매칭하는 것이 아니긴 하지만 그래도 실세계의 비유로 이해하기에는 좋다. 즉, 세상을 역할과 구현으로 구분한다.
26. 세상을 역할과 구현으로 분류하면 어떤 특징이 있는가? ⇒ 세상을 역할과 구현으로 구분하면 세상이 단순해지고, 유연해지면 변경도 편리해진다. 클라이언트는 대상의 역할 즉, 인터페이스만 알면 된다. 클라이언트는 구현 대상의 내부 구조를 몰라고 되고, 구현 대상의 내부 구조가 변경되어도 클라이언트는 영향을 받지 않는다. 또한, 클라이언트는 구형 대상 자체를 변경해도 영향을 받지 않는다.
27. 자바에서 역할과 구현을 분리했을 때 어떤 걸 중점적으로 봐야 할까? ⇒ 역할은 인터페이스, 구현은 인터페이스를 구현한 클래스나 구현 객체이기에 자바 언어의 다형성 활용해야 하고 그러면 객체를 설계할 때 역할과 구현을 명확히 분리하게 된다. 객체 설계 시 인터페이스라는 역할을 먼저 부여하고, 해당 역할을 수행하는 구현 객체를 만들어야 한다.
28. 객체의 협력? ⇒ 객체의 협력이라는 관계부터 생각해야 하는데, 일단 혼자 있는 객체는 없다. 클라이언트는 요청하는 자이고 서버는 응답하는 자이다. 수많은 객체 클라이언트와 객체 서버는 서로 협력 관계를 가진다.
29. 다형성의 본질이란? ⇒ 인터페이스를 구현한 객체 인스턴스를 실행 시점에 유연하게 변경할 수 있는데 다형성의 본질을 이해하려면 협력이라는 객체 사이의 관계에서 시작해야 한다. 다형성의 본질은 클라이언트를 변경하지 않고, 서버의 구현 기능을 유연하게 변경할 수 있다는 것이다. 
30. 역할과 구현의 분리를 정리해보면? ⇒ 실세계의 역할과 구현이라는 편리한 컨셉을 다형성을 통해 객체 세상으로 가져올 수 있다. 유연하고 변경이 용이하며 확장 가능한 설계가 가능하고 클라이언트에 영향을 주지 않는 변경이 가능하다. 그러려면 인터페이스를 안정적으로 잘 설계하는 것이 중요하다.
31. 역할과 구현의 분리에서 가지는 한계는 무엇인가? ⇒ 역할, 즉, 인터페이스 자체가 변하면 클라이언트, 서버 모두에 큰 변경이 발생한다. 예를 들어, 자동차를 비행기로 변경해야 한다면? 대본 자체가 변경된다면? USB 인터페이스가 변경된다면? 그러므로 인터페이스를 안정적으로 잘 설계하는 것이 중요하다. 
32. 91강에서 배운 걸 정리해본다면? ⇒ 자바에서는 다형성이 가장 중요하다. 디자인 패턴 대부분은 다형성을 활용하는 것이다. 스프링의 핵심인 IoC, DI도 결국 다형성을 활용하는 것이다. 다형성을 잘 활용하면 마치 레고 블럭을 조립하듯이, 공연 무대의 배우를 선택하듯, 구현을 편리하게 변경할 수 있다.
```
